# Commerce: fictional tests and a real-website exercise

These are two separate workflows using the local Python Workspace API:

- **Controlled demonstration:** ten fictional stores on `.example` domains, two synthetic observations per product, known answers, no network.
- **Live end-to-end exercise:** real candidate URLs and provisional templates, actual HTTP only after access review and explicit opt-in. The documented plan is **not run** and contains no product results.

Synthetic products never carry real retailer names or URLs. Live failures never fall back to synthetic products.

## Controlled demonstration

From the package root, with `pulsecrawl[workspace]` installed:

```bash
python -m examples.marketplace.premium_commerce.local --workspace ./commerce-demo --summary
```

Choose a fresh or empty workspace. The example creates one typed append-all dataset, ten exact fictional seeds, depth zero, a ten-page execution allowance and twenty-page lifetime allowance. Two ordinary Workspace executions receive generated HTML and robots responses from ControlledFetcher. There is no HTTP client or schedule.

SQLite staging, Parquet publication, version manifests, and DuckDB queries are real local runtime operations. Version 1 contains ten observations at fictional USD 120; version 2 contains twenty observations, with the second ten at fictional USD 99. The history check requires ten USD 21 decreases; a query pinned to version 1 still returns ten rows.

The fixture observation times are 2026-10-11 12:00 and 13:00 UTC. Runtime completion times and identifiers vary. The `controlled-demo-summary.json` projection omits workstation paths and UUIDs, and retains input hashes and checked outcomes. It was regenerated by running the revised fictional inputs, not by relabeling an old report.

The offline rate of 1,000 requests/second only keeps fixture tests quick; it is not a live setting. The first execution makes twenty fixture calls and the second ten because of the robots cache. These are function calls, not physical HTTP requests.

## Live End-to-End Case Study

`live-sources.json` matches the public [case-study manifest](https://github.com/pulsecrawl/research-datasets/tree/v0.2.0/live-case-study). It lists lululemon, Alo Yoga, Nordstrom, REVOLVE, Nike, Adidas, New Balance, On, HOKA, and UGG. All candidates are disabled pending access review. `recipes.py` contains thirty provisional scoped template entries; controlled strategy tests do not validate live-site compatibility.

From the package root:

```bash
python -m examples.marketplace.premium_commerce.live plan
python -m examples.marketplace.premium_commerce.live init --manifest ./reviewed-sources.json --workspace ./live-workspace
python -m examples.marketplace.premium_commerce.live run --manifest ./reviewed-sources.json --workspace ./live-workspace --network
python -m examples.marketplace.premium_commerce.live note --workspace ./live-workspace --stage inspection --text "Describe the actual outcome, including missing fields."
```

Before `init`, make a local copy of the manifest. Enable only eligible sources, set their `accessReview.status` to `reviewed`, document a non-empty `basis`, and supply a timezone-aware `reviewedAt`. Do not merely mark restrictive sources reviewed to force a run. The operator record does not override site restrictions.

The manifest supports at most two manually triggered executions, at least 24 hours apart, ten admitted pages per execution, and at most 0.5 requests/second (default 0.25). There is no automatic enrollment or unattended schedule. Each run independently caps physical attempts at twice the enabled source count, including robots, with no transport retries or automatic redirects. It accepts exact registered seeds only, blocks private-network destinations, and rejects duplicate product attempts.

A fresh robots check precedes product requests even if the workspace's robots cache contains an earlier allow. Unreadable, denied, or truncated robots responses stop product fetching. The additional wildcard guard can over-restrict rules and is not a complete RFC 9309 parser. Any applicable parsed crawl delay or request-rate interval can further slow dispatch. A robots response alone does not resolve the access review.

Responses are processed in memory with a 2 MiB limit; `store_raw_pages=False` prevents HTML archiving. There is no challenge solving, proxy rotation, authentication bypass, private API use, bot impersonation, or synthetic fallback.

### Evidence and practical analysis

`case-study.json` in the local workspace records:

- The resolved manifest and configuration digest.
- Execution identities, runtime status/counters, and committed dataset-version pointers.
- Attempted request URLs, UTC times, HTTP outcomes, body lengths and decoded-body SHA-256 values—not bodies, cookies, or full headers.
- Extracted observations, including nullable fields, plus separate counts for named products and prices with currencies.
- Operator notes about setup, execution, inspection, repeat runs, queries, and repairs.

A runtime status of `succeeded` does not imply successful extraction; zero product rows remain zero. Refusals and failed attempts remain visible. A manifest with no executions is a plan, not evidence. Unchanged real prices are valid observations; the live query does not require the fictional USD 21 change.

The report lists observations by URL and execution rather than inventing cross-store or cross-variant matches. Compare prices only when product/variant and currency context supports comparison. A checkout total, aggregate range, or recommended product must not be reported as the selected offer.

For SQL and pinned-version inspection use `Workspace.datasets.query(dataset_id, sql, version=...)`; the dataset identifier and committed version are in the report. `OBSERVATION_SQL` in `live.py` retains missing fields rather than excluding incomplete live products.

The runner reserves attempts before HTTP and counts failed or interrupted attempts toward its cap. A concurrent run is rejected by a local exercise lock. Investigate an interrupted run before removing a stale lock. Configuration changes require a new workspace: retain the prior report, record the repair, and do not merge it into a supposedly unchanged comparison. This small exercise helper is not an exactly-once HTTP system.

This bounded exercise demonstrates workflow behavior; it is not evidence of broad usability or live-site accuracy. **The repository contains no retained evidence of a real product run.** Do not upload an entire workspace or unreviewed notes. Review URLs, product fields, access notes, and metadata for sensitive information first.

## Extraction boundaries

The shared nullable schema distinguishes store from brand, product from first-offer identifiers, and current price from aggregate low/high prices. Regular price has no validated mapping and remains unset. Currency is never inferred from a symbol or locale.

JSON-LD follows the first offer; it does not enumerate all variants. Generic JSON-LD, CSS/microdata and product metadata strategies need actual value and negative-page checks before live accuracy claims. Source URL query parameters are retained; canonical product URLs may omit variant context. The fictional history query describes known variants, not universal product matching.
